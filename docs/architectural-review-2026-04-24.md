# Architectural Review — 2026-04-24

Point-in-time architectural review of the AI Workbench. Focus is on how
existing OSS pieces are integrated, not line-level code quality.

## Context

- **What this is:** a local-developer-first bootstrap for a personal / small-team
  AI workbench on a 16 GB ARM Mac under Rancher Desktop. Integrates chat +
  research UIs with an "MCP tool rack" of dockerized enterprise adapters (LDAP,
  ServiceNow) and agents that loop over them.
- **Target shapes:** two in parallel —
  1. **Single-host dev stack** (current repo): `127.0.0.1`-bound, single user.
  2. **k8s multi-user offshoot** (future): enterprise scale, multi-tenant, HA.
  The single-host repo is intended to **incubate** the k8s version. Divergence
  risk is a review lens throughout.
- **Stage:** pre-production / evolving greenfield.
- **Decision this feeds:** whether to harden this shape into a real platform
  vs. pivot to a more battle-tested agentic-platform skeleton.

## Custom code surface

1. **Bootstrap / config generator** — `scripts/bootstrap.py` (~800 lines). Reads
   `.env` + per-service `mcp-tool.yaml` manifests and renders LiteLLM config,
   Caddyfile, catalog page, and Open WebUI tool-connections.
2. **Ops scripts** — `scripts/{healthcheck,tool_stats,validate_env,query,open_notebook_model_config,generate_*}.py`.
3. **MCP data servers** — `services/ldap-mcp/server.py`, `services/servicenow-mcp/server.py`,
   `services/magic-fetch/server.py`.
4. **MCP agents (4 near-identical ReAct loops, ~500 lines each)** —
   `services/{ldap,servicenow,code,enrichment}-agent/server.py`.
5. **Vestigial** — `services/code-sandbox/` is dead code; replaced by Open Terminal.
6. **Registry bindings** — `registry/catalog.yaml` + `registry/apply.py`.

## Executive summary

Overall: **B** for the stated single-host dev goal. **C+** as a seed for a
k8s multi-user offshoot — good bones in some places, load-bearing assumptions
elsewhere that won't survive the port.

The best architectural decision in the repo is the manifest seam: per-service
`mcp-tool.yaml` files that `scripts/bootstrap.py` fans out into LiteLLM config,
Caddy routes, the catalog page, and Open WebUI's tool discovery. One file =
four artifacts. Preserve this shape unchanged into k8s.

Tracing is unusually disciplined — every custom agent emits OpenInference
spans that Phoenix renders natively, so you can trace an `enrichment-agent`
run end-to-end across sub-agents and tools.

**Top 3 strengths**
1. Manifest-driven tool plane (one YAML = routing + UI registration + catalog).
2. OpenInference tracing across the custom layer, with `magic_fetch` as a
   clean demand-signal pattern.
3. LiteLLM as a single model-gateway seam.

**Top 3 risks**
1. **Concurrency**: agents hold MCP session and JSON-RPC id state in
   **module-level globals** (`services/ldap-agent/server.py:188-189`, same in
   `servicenow-agent`, `enrichment-agent`). Fine for one user; guaranteed to
   corrupt sessions under concurrent load. Blocker for multi-user offshoot.
2. **Auth = none on every MCP endpoint** (`auth: mode: none` in all seven
   `mcp-tool.yaml` files), and `LITELLM_MASTER_KEY` is reused as model key,
   admin key, RAG key, and health bearer — single credential compromise =
   full platform compromise.
3. **Single shared Open Terminal** — no per-session isolation. Acceptable for
   the motivating workflow (single-user row enrichment); a hard fork for
   multi-tenant k8s.

## Lens-by-lens grades

### L1. Component selection — A−

OSS choices are idiomatic and well-fitted.

- LiteLLM (`docker-compose.yml:96-139`) as one provider gateway is idiomatic.
- Phoenix (`docker-compose.yml:56-72`) is right because agents emit OpenInference
  attributes Phoenix understands natively (`services/ldap-agent/server.py:309-311,373`).
- FastMCP is the official Python SDK for MCP servers — right default.
- Caddy is over-featured for `:8090` but exactly right for `.localhost`
  routing + file server + health proxying.
- mcpo is a clever choice: deterministic Python can call MCP tools via REST
  without a second MCP client. Load-bearing for the row-enrichment workflow.

**Missing categories**

- No **evaluation harness**. Phoenix has datasets/experiments — unused.
- No **cost tracking / budgeting** per user or agent. LiteLLM supports it.
- No **guardrails**. Flagged as "not yet implemented" in
  `docs/design-principles.md:95-99`.
- No **human-in-the-loop / approvals**. Latent because ServiceNow is
  read-only today.
- No **long-term memory** (each ReAct loop is one-shot).

### L2. Integration seams — B+

- The manifest seam is the right abstraction. A new tool is one directory +
  one Compose include line (`docker-compose.yml:18-26`) + bootstrap.
- **Leaky**: Open WebUI's MCP tool list is injected via a Compose include
  that rewrites an env var into JSON (`config/openwebui/compose.tool-connections.yaml`).
  Brittle — Open WebUI persists settings in its volume (README line 327 warns
  about this), so env may not always win.
- **Tight coupling**: `build_tool_connections()` in `bootstrap.py:469-492`
  hardcodes Open WebUI's specific JSON shape. Swapping Open WebUI = rewrite.
- **Half-seam**: Agentregistry is populated but no runtime path reads from
  it. A seam that doesn't seam anything.

### L3. Data flow — B

Persistent state lives in:

- `openwebui-data` (chat + persisted settings, partly authoritative over env)
- `litellm-db` (Postgres)
- `chroma-data` (single RAG namespace, no tenancy)
- `phoenix-data` (30-day trace retention)
- `surrealdb-data` (Open Notebook, `root/root` hardcoded at `docker-compose.yml:201`)
- `terminal-home` (shared across all sandbox jobs; jobs keyed by
  `/home/user/jobs/<job_id>/` but same container, same UID)
- `registry-data` (Agentregistry)
- **Module-level globals** in agent processes (MCP session state — shouldn't exist)

Trust boundary is effectively "anyone who can reach the docker network."
The `127.0.0.1` binding (`docker-compose.yml:37-38, 79, 211-212, 242-243`)
is the actual enforcement; the MCP layer itself trusts whoever calls it.

### L4. Control flow — B−

- **Orchestration**: four hand-rolled ReAct loops, structurally identical.
  `_parse_action` brace-counting duplicated four times. Max-steps 10/12/20/20.
- **Failure handling** is shallow: single `try/except` around each tool call
  pushes the error text into message history and continues (e.g.
  `enrichment-agent/server.py:512-516`). No retry, no backoff, no circuit
  breaker.
- **Agent-as-tool** (`enrichment-agent` → `ldap-agent` / `servicenow-agent`)
  is good — composes domain knowledge rather than flattening prompts. But
  delegated calls run sequentially.
- **Deterministic path** through mcpo is correct
  (`code-agent/server.py:134-172` system prompt): specialist agent plans
  once, sandbox Python hits mcpo per row. This is the motivating workflow.

### L5. Failure domains — C+

| Component down | Effect |
|---|---|
| Phoenix | Tracing silently fails (OTLP exporter drops). Agents still run. |
| LiteLLM | All agents fail AND Open WebUI chat fails AND Open Notebook fails. Hard single point of failure. |
| Chroma | RAG breaks in Open WebUI; rest fine. |
| ldap-mcp | ldap-agent + enrichment's LDAP branch fail; mcpo returns 502 on `/ldap/*`. |
| mcpo | Sandbox deterministic path breaks; specialist-agent path still works. |
| Open Terminal | code-agent, enrichment-agent, Caddy's `/sandbox/files/*` all fail. |
| Caddy | External routing dies; agents still talk internally. |
| Agentregistry | Nothing else breaks — not in any runtime path. |

**Concurrency failure**: module-level `_mcp_session_id` / `_jsonrpc_id`
(`ldap-agent/server.py:188-189` and siblings) means two concurrent requests
to one agent process will interleave JSON-RPC ids. Documented by reading the
code; not verified at runtime.

### L6. Observability — A−

- Every agent initializes its own OTEL pipeline with OpenInference
  `service.name` and `openinference.project.name`
  (`ldap-agent/server.py:54-69`).
- Spans are hand-constructed with the right attributes:
  `openinference.span.kind = AGENT/CHAIN/TOOL/LLM`, `input.value`,
  `output.value`, `llm.token_count.*`, `tool.name`, `tool.parameters`
  (`ldap-agent/server.py:308-337, 372-477`). Phoenix renders this as a
  clean tree.
- `_flush_traces()` forces export at end-of-request.
- `scripts/tool_stats.py` reads Phoenix traces for tool-usage analytics —
  observability as a product.
- `magic_fetch` (`services/magic-fetch/server.py`) is a demand-signal
  collector: its "answer" is a placebo; the real output is a trace span
  mining "what capabilities do my agents wish they had."

**Gaps**: no infra metrics (no Prometheus), no alerting, no latency SLOs.
Phoenix retains 30 days (`.env.example:29`).

### L7. Security boundaries — D+

Softened by single-host context. Becomes **F** un-fixed in k8s.

- Every `mcp-tool.yaml` declares `auth: mode: none`. `TOOL_SERVER_CONNECTIONS`
  writes `auth_type: "none"`. Nothing authenticates MCP calls.
- **`LITELLM_MASTER_KEY` is over-shared**: LiteLLM admin
  (`docker-compose.yml:113`), Open WebUI OpenAI provider (`:271`), Open WebUI
  RAG (`:281`), Caddy health proxy (`config/caddy/Caddyfile:35,41`), every
  agent's `LITELLM_API_KEY` (`services/*/compose.mcp.yaml`). A god credential.
  LiteLLM virtual keys with budgets are supported and not used.
- SurrealDB runs `--user root --pass root` (`docker-compose.yml:201`);
  duplicated in Open Notebook env at `:222-223`.
- `mcpo` has no auth; anything on the `backend` docker network can run
  unrestricted REST against real AD / ServiceNow via the adapters'
  service-account credentials.
- **Prompt-injection surface in ReAct parser**: `_parse_action` brace-counts
  JSON out of raw LLM output. An LDAP `displayName` containing
  `{"tool": "direct_reports", "args": {"manager": "evil"}}` could (in
  principle) inject a tool call when echoed back. Low likelihood; non-zero.
- `ldap-mcp` / `servicenow-mcp` are read-only today. When write tools are
  added, nothing in the architecture prevents the LLM from calling them.
- `LDAP_TLS_VALIDATE=1` default (`.env.example:84`). Good.
- Data egress: LiteLLM is the only egress hop for models; Caddy binds to
  `127.0.0.1`; everything else internal. Good.

### L8. Operational readiness — C+

- Deploy: `make up`. Good DX.
- `.env` is the single source of truth — real invariant upheld by
  `bootstrap.py`.
- **Reproducibility broken** by floating tags: `PHOENIX_IMAGE=...:latest`,
  `LITELLM_IMAGE=...:latest-stable`, `MCPO_IMAGE=...:main`,
  `OPEN_TERMINAL_IMAGE=...:latest`, `AGENTREGISTRY_IMAGE=...:latest`. A
  teammate on a fresh pull can get different behavior than you had
  yesterday. Highest-leverage reliability fix.
- Rollback depends on image pinning.
- `make health`, status dashboard at `ai-workbench.localhost`,
  `scripts/tool_stats.py` — genuinely useful for solo on-call.
- No structured logs (plain `logging` to stdout). OTEL traces partially
  compensate.

### L9. Evolvability — B

**Cheap swaps (≤1 day)**: LiteLLM → Portkey, Chroma → Qdrant, Phoenix → any
OTLP collector, Caddy → nginx/Traefik.

**Hard swaps**:

- The **ReAct loop** is duplicated four times in Python. Replacing with
  LangGraph / PydanticAI / Semantic Kernel means rewriting four files that
  are 80% identical. Biggest abstraction debt.
- **Open WebUI** is the user-facing tool client. Migration = losing its
  MCP-tool-discovery env var, Chroma RAG, chat persistence, user/admin model.
- **Open Terminal** as sandbox substrate. The HTTP contract
  (`code-agent/server.py:195-300`) would survive a backend change; the
  contract is narrow and reasonable.

### L10. Documentation vs reality — B−

Docs are unusually honest (`docs/design-principles.md:63-99` flags
implemented/partial/TODO). Drift log in §8.

## What's working — preserve these

1. The `mcp-tool.yaml` → bootstrap seam. One file, four artifacts. Gene that
   both single-host and k8s should inherit.
2. LiteLLM as the only model egress — single place for org-wide policy,
   logging, provider swaps.
3. OpenInference spans in agents. Keep the pattern when the ReAct loops are
   deduped.
4. `magic_fetch` as demand-signal collector.
5. Deterministic fan-out via mcpo. This is the motivating Open Terminal
   workflow; preserve the pattern in both single-host and k8s flavors.
6. Compose profiles (`core` / `tools` / `notebook` / `debug`) for memory budget.
7. Binding to `127.0.0.1`. Right default.
8. Honest design docs with implemented/partial/TODO tables.

## Suggested changes — prioritized

### P0 — harden before multi-user (and improve single-host)

**P0-1. Kill module-level MCP session globals.**
`services/ldap-agent/server.py:188-189`, `services/servicenow-agent/server.py:273-274`,
`services/enrichment-agent/server.py:168-169`. Scope session state to the
tool call (small `MCPClient` per `run_agent()`, or lifespan-bound and keyed
by upstream URL). ~1 afternoon × 3 agents.

**P0-2. Pin every image tag.**
`.env.example:9,11,14,16,17,18`. Add a `make refresh-images` for deliberate
updates. 30 minutes.

**P0-3. Stop re-using `LITELLM_MASTER_KEY` everywhere.**
Turn on LiteLLM virtual keys. Generate per-agent and per-UI keys at bootstrap;
master stays only in `litellm:`. Add per-key budgets. ~2 days.

**P0-4. Fix SurrealDB `root/root` hardcode.**
`docker-compose.yml:201,222-223`. Use the `__GENERATE__` pattern. 15 minutes.

**P0-5. Delete `services/code-sandbox/`.**
Dead code; Open Terminal replaced it. 2 minutes.

### P1 — required before k8s offshoot; valuable single-host

**P1-1. Extract a tiny agent framework.**
4 × ~500 lines of copy-paste ReAct + OTEL + MCP JSON-RPC. New
`services/_agent_core/` or internal package. Interface:
`run_react_agent(system_prompt, tools, question, *, max_steps, model)`.
OpenInference span emission lives there. 3–5 days including migrating all
four agents. Alternative: adopt PydanticAI or LangGraph.

**P1-2. Make Agentregistry load-bearing — or remove it.**
Option A (recommended): have `bootstrap.py` read from Agentregistry (or push
`mcp-tool.yaml` into the registry as source of truth). One schema, both
shapes share it. 2–4 days.

**P1-3. Wire `auth: mode: bearer` through the tool plane.**
Bootstrap generates per-tool tokens; Caddy `handle_path /mcp/<slug>/*`
enforces; `TOOL_SERVER_CONNECTIONS` gets `auth_type: bearer`; agents pass
bearer when calling each other. 1–2 days.

**P1-4. Evals and golden sets in Phoenix.**
10–20 Q/A per agent as golden sets in `tests/evals/`. `make eval` target
runs `phoenix.experiments`. 2–3 days.

**P1-5. Derive Caddy health routes from manifests.**
`bootstrap.py:329-340` hardcodes the list alongside the manifest-derived
tool list. Risk of drift. Half a day.

### P2 — ready the offshoot

- **P2-1**. Explicit policy layer (per-agent tool allowlist, path protections,
  rate limits). `risk_tier` / `auth` already declared; enforce.
- **P2-2**. Replace `TOOL_SERVER_CONNECTIONS` env-var hack with a runtime
  registration flow (Open WebUI plugin, or proxy exposing Agentregistry as
  tool source).
- **P2-3**. Structured JSON logging via shared library.
- **P2-4**. Per-session sandbox substrate for multi-user workloads — k8s
  Job / Pod per execution, or e2b / Modal. Single-host keeps Open Terminal;
  it serves the motivating row-enrichment workflow well.
- **P2-5**. Prometheus metrics on LiteLLM, Caddy, agents.

## Incubator story — does this seed the k8s offshoot?

**Viable as an incubator if the five steps below are taken; divergence is
likely otherwise within ~6 months of parallel development.**

### What ports cleanly (unchanged)

- Every `mcp-tool.yaml` manifest → Helm values fragment or CRD.
- LiteLLM config → same YAML on a StatefulSet. Virtual keys + budgets apply
  identically.
- OpenInference tracing → point OTLP at a different collector; no agent
  changes.
- MCP data servers (`ldap-mcp`, `servicenow-mcp`) → stateless Deployments.
- `magic_fetch` → unchanged.
- mcpo → unchanged Deployment.
- Agentregistry → gains its purpose in the k8s world; the overkill pays off.

### What needs a rewrite, not a port

1. Agent concurrency (P0-1). Module globals must be gone before any multi-user deploy.
2. Open Terminal as sandbox (P2-4). One shared container is a non-starter
   for multi-tenant. Keep its HTTP contract; swap the backend.
3. Open WebUI tool discovery. `TOOL_SERVER_CONNECTIONS` env injection fights
   Open WebUI's persisted settings. Needs a real plugin or proxy in k8s.
4. Caddy → ingress. Preserve the idea (manifests → routes); rewrite the
   emitter.
5. Secrets. `.env` → External Secrets / Vault. `__GENERATE__` pattern
   becomes bootstrap Jobs or sealed-secrets.

### Five concrete steps to make this a real incubator

1. **Freeze the `mcp-tool.yaml` schema.** Add `schema_version: 1`. Both
   single-host bootstrap and the future k8s chart read the same schema.
2. **Do P0-1 and P0-3 in the single-host repo first.** Code that hides
   multi-user assumptions inside single-user implementations diverges
   fastest when forked.
3. **Do P1-1 (shared agent core) before agent #5.** Each new agent coded
   in the current style is another file to rewrite for k8s.
4. **Do P1-2 (Agentregistry as source of truth).** Keep one registry schema
   across both shapes; shared `apply.py`, evals, ops scripts — different
   runtimes.
5. **Ship a thin shared library** (`lib/workbench-core/` as git submodule
   or local package): manifest schema loader, agent-core ReAct runtime,
   OTEL/OpenInference helpers, MCP JSON-RPC client. Both repos pull from
   it.

### The one thing not to carry forward

The hand-rolled ReAct loops. Replace with a ~300-line internal library or
PydanticAI before forking. Multiplying four copies × two repos × future
agents is the worst-case trajectory.

## Reference comparison

**Anthropic-style "agents as building blocks + evals"**: matches on tracing
and agent-as-tool composition. Diverges on evals (missing), registry
(present but unused), safety (none). Divergence partly intentional
(single-user), partly accidental (evals/guardrails flagged as TODO).

**"LangGraph + Temporal + OTel" enterprise shape**: has the gateway and
observability layer. Missing a real workflow substrate — hand-rolled ReAct
is the trade. Acceptable single-host; limiting in k8s (no checkpointing, no
resume-from-failure, no durable long-running agents).

Divergences read as intentional for single-host and accidental for the k8s
offshoot.

## TL;DR

The manifest → bootstrap → multi-artifact generation seam is genuinely
good — preserve it. Observability is unusually strong — preserve it. The
rest is a well-assembled dev stack with three load-bearing assumptions that
won't survive a port to k8s: module-level agent globals, a god credential,
and a shared sandbox. Fix P0-1, P0-3, P2-4, plus pin image tags, delete
dead code, and extract the ReAct loop into one shared implementation — and
this is a credible incubator for the k8s offshoot. Skip those and the
offshoot becomes a rewrite.
