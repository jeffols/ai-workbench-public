Security Boundary Analysis

  • All host ports bind to 127.0.0.1 only — no external exposure
  • Caddy bridges all 3 networks — it's the single gateway
  • Data servers (ldap-mcp, servicenow-mcp, sightline-mcp) are tools-only — not reachable from proxy
  • Agents bridge agents+tools — they can reach everything on both networks
  • litellm-db :5432 is exposed to host — unnecessary for production
  • External APIs (LDAP, ServiceNow, Sightline) are called outbound only — no inbound from internet

Bridge Containers (dual-network)

These 10 containers sit on both agents and tools networks. They can route traffic between the two — the network boundary is only as strong as these containers' code.

  • caddy, phoenix, mcpo — infrastructure, expected
  • open-terminal — needs tools (mcpo) and agents (for API key auth)
  • All 5 agents bridge both networks — necessary today, but in k8s these should be separated

Agent-as-Tool Pattern

enrichment-agent does NOT call ldap-mcp or servicenow-mcp directly. It delegates to specialist agents that carry domain knowledge in their system prompts. Each specialist runs its own ReAct loop — it's a two-level agentic system.

LLM Call Count

A typical enrichment request makes 6+ LiteLLM calls from the orchestrator, plus 2-4 per specialist. Total: ~10-14 LLM round-trips. Each costs tokens. The deterministic sandbox path avoids this for the actual data merge.

Not Delegated: code-agent

Despite existing as a service, code-agent is NOT called by enrichment-agent. The enrichment-agent calls Open Terminal's HTTP API directly. code-agent is a standalone orchestrator for code-only tasks routed separately.

Protocol Stack at Each Hop

  • User → WebUI: HTTP (browser)
  • WebUI → Caddy: HTTP MCP (tool connection)
  • Caddy → enrichment-agent: HTTP reverse proxy (slug routing)
  • enrichment-agent → specialist agents: HTTP MCP JSON-RPC 2.0 (with session init + Mcp-Session-Id header)
  • specialist agents → data servers: HTTP MCP JSON-RPC 2.0 (same protocol, different session)
  • enrichment-agent → Open Terminal: plain HTTP REST (not MCP — different API)
  • All agents → LiteLLM: OpenAI-compatible HTTP (/v1/chat/completions)
  • All agents → Phoenix: OTEL HTTP exporter (batched spans)

Highest Fan-In: LiteLLM

8 callers — openwebui, all 5 agents, open-notebook, and (indirectly) litellm-db. Every reasoning step in the system flows through this single gateway. It's the most critical chokepoint.

Highest Fan-Out: enrichment-agent

6 callees — litellm, phoenix, ldap-agent, servicenow-agent, sightline-agent, open-terminal. Most connected component in the system. Failure in any dependency cascades here first.

Highest Fan-Out: Caddy

15 callees — routes to every MCP service, both UIs, litellm, and phoenix. But this is routing, not logic — Caddy is stateless and replaceable. The enrichment-agent fan-out is more architecturally significant.

Reading the Matrix

  • Data servers (ldap-mcp, servicenow-mcp, sightline-mcp) have fan-out of exactly 1 — they call only their external API. Clean adapters.
  • Agents have a consistent pattern: LiteLLM (reasoning) + one data server (tools) + Phoenix (telemetry). Symmetric design.
  • enrichment-agent breaks the pattern — it calls 3 agents + sandbox but NOT data servers. This is the agent-as-tool pattern.
  • open-terminal → mcpo → data servers forms the deterministic pipeline. No LiteLLM in that chain.
  • No circular dependencies. The graph is a DAG from UI → agents → data servers → external.

A4 Phoenix Span Trace — End to End

Following one user query from Open WebUI through the enrichment-agent to data servers. Each box is an OpenInference span as it would appear in Phoenix. Dashed red boxes are observability gaps — hops with no span emitted.

What Gets Traced

  • Every agent ReAct step (CHAIN span)
  • Every LiteLLM chat completion (LLM span)
  • Every tool call from an agent (TOOL span)
  • The overall agent task (AGENT span)
  • LiteLLM's own request traces (provider-level)

What Does NOT Get Traced

  • Open WebUI → Caddy routing
  • Caddy → agent forwarding
  • Specialist agent internals (separate trace context)
  • Open Terminal code execution
  • mcpo → data server MCP calls
  • Data server → external API calls

Observability Coverage: ~40%

Of the full request chain (User → WebUI → Caddy → Agent → LiteLLM → Agent → Data Server → External API), Phoenix only sees the agent's internal reasoning and LiteLLM calls.

  • Well-traced: agent ReAct steps, LLM calls (model, tokens, latency), tool call inputs/outputs
  • Separate traces: specialist agent internals (linked by propagation headers but not nested)
  • Invisible: HTTP routing (Caddy), data server internals, external API calls, sandbox execution, mcpo bridging

Recommendations to Close Gaps

  • Add OTEL to data servers (ldap-mcp, servicenow-mcp, sightline-mcp) — instrument the external API calls to see where time goes
  • Add OTEL to Open Terminal — trace code execution time and mcpo REST calls from sandbox
  • Add OTEL to mcpo — trace the MCP→REST bridge hop, especially latency per data server
  • Ensure trace context propagation is end-to-end — enrichment-agent injects headers but specialist agents may start new roots instead of continuing the trace
  • Consider: is Caddy tracing worthwhile? Probably not — routing latency is negligible (~5ms)
