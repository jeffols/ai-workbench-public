Key Idea: Manifest-Driven

Each data server publishes one mcp-tool.yaml. bootstrap.py reads them and generates all routing rules, catalog entries, and UI connections. Adding a tool = writing one YAML file.

Key Idea: Agent-as-Tool

Agents are MCP servers that themselves call other MCP servers. The enrichment-agent delegates to specialist agents — it never touches data servers directly. Two-level agentic system.

Key Idea: Two Paths

LLM-driven path: agent reasons step-by-step. Deterministic path: LLM writes code once, sandbox executes it row-by-row via REST. Both paths use the same data servers.

  • Transport: HTTP streamable-http

Agents (Brains)

  • ReAct loop: reason → tool-call → observe → repeat
  • Each backed by LiteLLM for LLM reasoning
  • enrichment-agent delegates to specialist agents
  • Domain logic lives in system prompts only

04 Two Data Paths

The system has two fundamentally different execution modes — understanding this distinction is critical.

Path A: LLM-Driven (Agent Loop)

User asks a question → agent reasons → calls tools → synthesizes answer. Every step involves the LLM.

Path B: Deterministic (Code Pipeline)

LLM writes Python code once → sandbox executes it row-by-row against enterprise APIs via REST. No LLM in the execution loop.

Why two paths?

Path A is great for questions: "Who reports to Jane?" — the LLM reasons about what to look up. Path B is for bulk operations: "Enrich this 500-row CSV with directory department and ticket counts" — the LLM writes a pandas script once, then the sandbox executes it deterministically. This is the core insight behind Open Terminal: LLM composition over tabular data.

07 Assumptions & Risks

What the architecture currently assumes, and where those assumptions break.

Active Assumptions

Holding

Single user, single host

Module-level globals, shared sandbox, no auth on MCP endpoints. Works today because only one user is on the system.

Holding

LiteLLM as universal model seam

All consumers (agents, UIs, future CLI) route through LiteLLM. Provider-switching, cost tracking, and fallback all centralized.

Holding

Manifest-driven generation

One mcp-tool.yaml per service → bootstrap generates 4 config artifacts. Adding a tool is a YAML file, not a config change in 4 places.

Holding

Read-only adapters are safe without auth

No write operations exposed. Data servers only query enterprise systems. Risk is contained to information disclosure within the private network.

Known Risks

Breaks at scale

Module-level session globals

Agents use module-level variables for MCP JSON-RPC ID tracking. Concurrent requests will collide. Must fix for k8s multi-user.

Breaks at scale

No MCP endpoint authentication

All services have auth: mode: none. Internal Docker network is the only boundary. k8s network policies won't be enough.

Breaks at scale

Shared Open Terminal sandbox

All users share one sandbox container. No per-user file isolation. User A can see User B's uploaded files.

Unknown

ReAct loop reliability

Hand-rolled ReAct loops lack retry, timeout, and checkpoint semantics. LangGraph migration is planned but not scheduled.

Unknown

Agentregistry value proposition

Optional profile with 3 containers. Must prove value by 2026-06-24 or be removed. Currently disconnected from main data flow.

Additional visualizations and analysis that would deepen understanding of the project.

Diagram

Network Topology Map

Docker network boundaries (agents, tools, proxy) with exact container membership. Shows what can talk to what at the network level — critical for understanding the security boundary.

Diagram

Bootstrap Generation Flow

Detailed trace of what bootstrap.py reads vs. writes. Input manifests → template logic → output artifacts. Reveals the full "blast radius" of changing one mcp-tool.yaml.

Diagram

Enrichment-Agent Delegation Graph

Sequence diagram showing how enrichment-agent orchestrates specialist agents. Shows the cross-agent MCP call chain, including the dual path (LLM-driven queries vs. deterministic code-agent pipeline).

Prompt

"Walk me through a CSV enrichment"

End-to-end trace of a user uploading a CSV and getting it enriched. Covers: file upload, code generation, sandbox execution, mcpo bridge, data server calls, result download.

Prompt

"What breaks when we add a second user?"

Stress-test the single-user assumptions. Systematically identifies every global, shared resource, and missing auth boundary that would fail with concurrent users.

Prompt

"Diff the Compose and future Helm deploy"

Side-by-side comparison of what changes between the single-host Compose stack and the k8s Helm target. Services, networks, storage, auth, isolation.

Artifact

Dependency Matrix (who calls whom)

A heatmap showing every service-to-service dependency. Highlights the enrichment-agent as the highest-fan-out component and LiteLLM as the highest-fan-in.

Artifact

Cost Model Sketch

Estimate LLM token spend per operation type (single query vs. 500-row enrichment). Shows why the deterministic path matters for cost — one code-gen call vs. 500 agent reasoning loops.

Exercise

"Add a new data source" walkthrough

Step-by-step guide: write mcp-tool.yaml → implement MCP server → bootstrap → wire agent → test via WebUI. Proves the manifest-driven generation seam works.

Exercise

"Kill one seam" thought experiment

For each of the 6 seams: what happens if you remove it? What couples? What breaks? Reveals which seams are load-bearing vs. convenience.

Prompt

"Trace a Phoenix span end-to-end"

Follow one user query from Open WebUI → agent → LiteLLM → data server, and show what each hop records in Phoenix. Reveals observability gaps.

Artifact

Migration Checklist: ReAct → LangGraph

Per-agent inventory of what changes: state management, tool registration, prompt format, error handling, checkpoint storage. Sizes the LangGraph migration.
